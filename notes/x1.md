## What is built

`runPreview` now returns `stats`, `cellIssues` and `highlights` on every call. `stats` is all zeros when
cleaning is off. `highlights` is `[]` when `outputId` is null. Otherwise highlights are computed for
**every** output that has `conditionalFormats`, whatever its `fileType`, so CSV previews and report
images are coloured too (request from X2/X3). Only the CSV file itself has no formatting.

## Answers to other agents

**Pivot layout (X2).** Your assumptions are right:
- The first column (`key: "label"`) holds the row labels. They are sorted with numbers first, then dates, then text, and `"(blank)"` comes last.
- With `columnKey`, the value columns are `col_0`, `col_1` and so on. They are sorted the same way and capped at 50; `truncatedColumns: true` means the data had more distinct values. The **last column is `key: "total"`, the row totals**.
- **Without `columnKey` there is no separate total column.** The result is `[label, value]` (`key: "value"`, for example "Sum of Amount" or "Count"). That single value column is the row total, so "the last column is the row totals" still holds.
- The **last row is always `["Total", ...column totals, grand total]`**.
- The totals always cover all the data, including rows beyond `limit` and columns beyond the cap.
- `totalRows` is the number of distinct row labels. `rows.length` is `min(limit, totalRows) + 1`.
- A cell with no rows is `""`. Sum, average, min and max use the value field's column format; count is a plain integer.
- Thrown errors use `INVALID_DEFINITION`: a missing or unknown `rowKey`, an unknown `columnKey` or `valueKey`, an unknown `fn`, or `sum`/`avg`/`min`/`max` without a `valueKey`.

**Unknown cleaning ids (coordinator).** These are ignored and never cause a throw.
- If some `removeDuplicates.keys` / `fillBlanks.fieldIds` still exist, only those are used.
- If **all** the chosen ids are gone, that option is **skipped** (it does nothing). It does not fall back to `[]`: comparing "every field" or filling "every field" is not what the user picked.
- Validation reports both cases as a `warning`: scope `'cleaning'`, id `'removeDuplicates'` or `'fillBlanks'`, code `missing-field`.

## Deviations from CONTRACTS.md section 12 and lib/workerClient.js (exact)

1. **`lookupInfo` also has `duplicateKeys`**, as the task asked. It counts the distinct lookup keys that appear more than once, not the extra rows. The JSDoc of `loadTable` in `lib/workerClient.js` does not list it yet (request below).
2. **Issue scope `'cleaning'` is new.** Cleaning issues use `scope: 'cleaning'` and `id: 'removeDuplicates' | 'fillBlanks'`. The Mapping step's `groupMappingIssues` puts them in `general`.
3. **Highlight rule issues** use `scope: 'output'` with **`id` = the rule id** (not the output id), plus `outputId`. `issuesForOutput` (by `outputId`) finds them.
4. **`buildOutputFile` is now async** (it returns a Promise), because the JSZip post-processing is async. Its only callers are the worker and the tests. `writeXlsx` and `writeXlsxBook` are unchanged and synchronous. `writeStyledXlsx` is new and async.
5. **`isEmpty` and `notEquals` highlight rules map to an extra Excel rule.** Each column with rules gets one leading `containsBlanks` rule with `stopIfTrue`. This is needed because Excel's `cellIs` treats a blank cell as 0 / `""` (so "less than 50" would colour blanks), while the app's rule semantics never let a blank match a comparison. That leading rule:
   - carries the style of the first `isEmpty`/`notEquals` rule, so `isEmpty` -> `containsBlanks` as specified;
   - or has no format at all (a guard), when the column only has comparisons.

   Every rule has `stopIfTrue="1"`, so the first matching rule wins, exactly like the preview.
6. **Date rule values without a time compare whole days**, as filters do. So `equals 2024-01-05` is written as `cellIs between 45296 and 45296.99999`, `notEquals` as `notBetween`, and `gt d` as `greaterThanOrEqual d+1`. All of them are still `cellIs`.
7. **`contains`** becomes `containsText` with `SEARCH`, and Excel's wildcards `* ? ~` are escaped, so it stays a literal substring test like the preview.
8. **Pivot without `columnKey`** has two columns (see above), not a separate total column.

## Assumptions

- **Cleaning order:** trim -> remove empty rows -> fill blanks -> remove duplicates.
  - Trimming first means whitespace-only text is empty. Text that ends up `""` becomes `null`.
  - Filling before de-duplicating means rows that differ only by a filled blank count as duplicates.
  - Fills on a row that is then removed as a duplicate are not counted in `blanksFilled`.
- **"Every field" means every field of the definition**, not only the fields an output keeps. Every output of a workflow sees the same cleaned rows, and the stats match across outputs that share the filter.
- **Duplicate detection ignores case for text**, like Excel's Remove Duplicates. It does not trim; `trimText` does that. Numbers compare by value and dates by time; the number `5` and the text `"5"` differ.
- **Fill value typing:** a fixed fill value is typed like the default transform (strictly numeric text becomes a number) and then coerced to the field's column format or source type. So `"0"` fills a number column with 0, and `"2024-12-31"` fills a date-formatted column with a real date.
- **`'error'` cell issues** mark:
  - a failed formula on that row (only while the cell is still empty);
  - every cell of a field whose formula does not compile or whose source column does not exist;
  - a value that does not fit a trailing number or date format.

  A field with no source chosen yet shows `'blank'`.
- **Lookup keys:**
  - Trimmed, inner whitespace collapsed, case-insensitive.
  - Numbers and unambiguous numeric text match by value: `101`, `"101"` and `"101.0"` match, and so do `1200` and `"1,200"`. The code `"00101"` does not match `101`.
  - Dates match their `YYYY-MM-DD` text, and empty keys never match.
- **Lookup columns:** chosen lookup columns are matched by name loosely (case and spaces), like source columns. A chosen column that is missing gives a warning and is skipped.
- **Lookup when not configured:** `lookup.enabled` with a key column not chosen gives `lookupInfo.applied: false` and a warning. `lookup: null` or `enabled: false` gives `lookupInfo: null`. The `"lookup"` dataset never joins onto itself.
- **`sheetStyle` defaults:** an xlsx output without `sheetStyle` (older definitions) gets the schema defaults, a bold, frozen header. A direct `styleXlsx` call without `sheetStyle` styles nothing.
- **Re-compression:** the styled file is re-deflated by JSZip at level 3. That also roughly halves xlsx size compared with SheetJS's own deflate (25.9 MB -> about 12 MB for 100k x 20).

## Known gaps

- **Text against a number in Excel.** Excel treats any text as greater than any number, and the app does not. So a `gt`/`gte` rule with a numeric value colours text cells (such as "n/a") in a column that is not number-formatted in Excel, but not in the preview.
- **`contains` on dates.** On a date column, `contains` searches the serial number in Excel but the `YYYY-MM-DD` text in the app.
- **No Excel or LibreOffice run.** Neither is installed here, and I could not get the ECMA XSD for xmllint. The checks were openpyxl plus tag-balance and schema-order tests on worksheet, styleSheet and workbook XML.
- **Re-deflating time.** Styled xlsx exports re-deflate the sheet: +0.5 to 1.5 s at 100k rows. Native `CompressionStream` would be faster but JSZip cannot use it.
- **Sheet file paths.** `styleXlsx` addresses sheets as `xl/worksheets/sheetN.xml`, which is how SheetJS names them. It does not resolve the workbook relationships.
